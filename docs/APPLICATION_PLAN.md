# From Skill to Application: Migration Plan

## 1. Where things stand today

Claude Coach currently has two halves that don't quite match anymore:

- **`README.md`** describes an older product: a triathlon coach that syncs Strava, driven by a
  Claude.ai/Claude Code **Skill**.
- **`skill/SKILL.md`** (last touched today, `d5c0d54` → `7841565`) describes the *current*
  direction: a running + strength coach, sourcing training history from a **COROS MCP
  connector** instead of Strava, with manual entry as the fallback. The README is stale.

This plan targets the current direction (running + strength, COROS-first, manual fallback), and
calls out where Strava-era code (`src/strava/*`, `src/db/*`) still fits or should be retired.

Regardless of which data source wins, the core problem is the same: **all of the coaching
intelligence lives in `skill/SKILL.md` and `skill/reference/*.md` as instructions for a human's
Claude session to follow.** Nothing in `src/` calls the Claude API. What *is* real code today:

| Piece | What it does | Reusable as-is? |
|---|---|---|
| `src/schema/training-plan.ts` | The `TrainingPlan` JSON contract | Yes — this is the app's data model |
| `src/viewer/*` (Svelte) | Calendar UI, edit/complete workouts, export to `.ics`/`.zwo`/`.fit`/`.mrc` | Yes — already a real, working app, just packaged as a single static HTML file |
| `src/strava/*`, `src/db/*` | Local OAuth + SQLite sync of Strava activities | Partially — sound logic, wrong storage model (local file, single user) |
| `src/cli.ts` | `sync` / `auth` / `render` / `query` commands | Superseded by a server, but `render`'s template-stamping trick informs the new plan-serving route |
| `skill/SKILL.md` + `skill/reference/*.md` | Coaching knowledge (assessment, zones, load management, periodization, workout library, race day) | Yes, but repurposed: goes from "instructions a human's Claude reads" to "context fed into a server-side Claude API call" |

So this is less "rewrite the coach" and more "move the reasoning from a human-operated Claude
session into a service that calls the Claude API itself, and replace the conversational
Q&A/AskUserQuestion flow with real UI."

## 2. What "application" means here

Today, using Claude Coach requires: a Claude.ai or Claude Code account with Skills enabled, the
skill installed, and (for live data) a COROS MCP connector or Strava API keys typed into a chat.
The output is a static HTML file generated by hand-running CLI commands.

The target is a **standalone web app** that:

- Needs only an Anthropic API key on the *server* — end users don't need any Claude access at all.
- Replaces the conversational onboarding (`AskUserQuestion`, free-text data gathering) with an
  actual multi-step form/wizard.
- Calls the Claude API directly, server-side, to do the plan authoring — using the existing
  reference docs as system-prompt content, not as instructions read by a human's assistant.
- Serves the existing Svelte viewer live from a backend/plan ID, instead of a hand-rendered
  single-file HTML export (though static export should remain, as an offline artifact).
- Persists plans and connected-account data per user, instead of per-local-machine files and
  browser localStorage only.

## 3. Target architecture

Recommend a single full-stack app (SvelteKit is the natural fit — the viewer is already Svelte —
but Next.js is fine if preferred) with:

```
apps/web/
├── routes/
│   ├── onboarding/            # wizard: event, constraints, data source choice
│   ├── connect/strava/        # OAuth callback (COROS: see §4.2)
│   ├── plan/[id]/             # the existing viewer, fed live data instead of embedded JSON
│   └── api/
│       ├── generate-plan/     # POST: kicks off plan generation
│       ├── plans/[id]/        # GET/PATCH: fetch/update a plan (edits, completions)
│       └── strava/sync/       # background sync job trigger
├── lib/
│   ├── coach-engine/          # NEW — the productized "skill"
│   │   ├── prompt.ts          # builds system prompt from skill/reference/*.md
│   │   ├── tools.ts           # data-fetching tool definitions (Strava/COROS/manual)
│   │   ├── generate.ts        # Claude API call + tool loop + schema validation/repair
│   │   └── assessment.ts      # deterministic aggregation (weekly volume, benchmarks) from synced data
│   ├── schema/training-plan.ts     # moved from src/, unchanged
│   └── viewer/                     # moved from src/viewer, unchanged
└── db/                          # multi-tenant schema (see §5)
```

### 3.1 The coach engine (the actual "skill → code" conversion)

This is the core of the migration. Concretely:

1. **Prompt assembly**: concatenate `SKILL.md`'s coaching principles + the relevant
   `reference/*.md` files into a system prompt. Keep these files as the single source of
   coaching knowledge — editing `reference/zones.md` should change app behavior exactly like it
   changes skill behavior today. Don't fork the content.
2. **Tool-use loop**: give Claude API tool definitions equivalent to the COROS MCP tools
   (`queryUserInfo`, `querySportRecords`, `queryTrainingLoadAssessment`, etc.) or a Strava
   equivalent, backed by real server-side implementations instead of a user's MCP connector.
   Let Claude call them mid-conversation exactly as the skill instructs it to, using the
   Messages API's tool-use loop (see the `claude-api` skill/reference for current SDK patterns).
3. **Structured output + validation**: after Claude produces the plan JSON, validate against a
   zod schema generated from (or mirroring) `training-plan.ts`. On validation failure, feed the
   errors back to Claude for a repair turn rather than failing outright — this replaces the
   implicit "human notices something's off" safety net.
4. **Deterministic pre-aggregation**: things like weekly volume, longest session, and consistency
   are pure arithmetic over synced activities (`assessment.md`, `load-management.md` math). Do
   this in code, not in the LLM call — cheaper, deterministic, and testable — then hand the
   *summarized* assessment to Claude for the qualitative judgment (foundation level, limiters,
   strengths) and plan authoring, matching how the skill already separates "aggregate the data"
   from "interpret it."
5. **Athlete validation, as UI not chat**: Phase 2 of the skill ("present assessment, ask
   validation questions, adjust") becomes a review screen — show the generated assessment,
   let the user edit fields or flag injuries/constraints, then regenerate. This is a second
   `generate-plan` call with the same conversation/tool state plus the user's corrections, not a
   new conversational round-trip.

### 3.2 The viewer

Almost no changes needed to the Svelte components themselves. The main change: `App.svelte`
currently reads plan data from an embedded `<script type="application/json" id="plan-data">` tag
stamped in by `claude-coach render`. Swap that for a `load` function that fetches
`/api/plans/[id]` on the live app, while keeping the static-export path (`render`) working for
users who want a portable offline HTML file — that's a genuinely nice feature worth keeping, not
retiring.

Local edits (marking workouts complete, moving sessions) currently save to `localStorage` only.
For the app version, sync those back to the backend (`PATCH /api/plans/[id]`) so a plan is
consistent across devices, while keeping localStorage as an offline-first cache.

## 4. Data sources

### 4.1 Strava (existing code)

`src/strava/oauth.ts` and `api.ts` are solid and mostly portable — the OAuth dance and API calls
don't change. What changes is storage: tokens move from a local config file (`src/lib/config.ts`)
to a per-user row in the app's database, and sync becomes a server-triggered job instead of a CLI
command run by hand.

### 4.2 COROS (net-new — this is the gap)

The skill assumes the *user's own Claude client* has a COROS MCP connector configured — that's a
third-party integration living outside this repo, in the user's Claude.ai/Code settings. A
standalone app can't lean on that. Options, in order of preference:

1. **Direct COROS API integration**, if COROS documents a developer/partner API — build a
   `src/coros/` module mirroring `src/strava/` (OAuth or key-based auth + activity fetch),
   replacing the MCP tool calls with real HTTP calls, server-side.
2. **Speak MCP directly from the backend**, if the COROS MCP server the skill relies on is
   reachable outside a Claude client — an app backend can be an MCP client too, calling the same
   server's tools programmatically. Worth investigating before ruling it out, since it would let
   `reference/queries.md`'s tool list carry over almost unchanged.
3. **Manual entry only for COROS users in v1** if neither exists yet — `SKILL.md`'s "Option B"
   fields already define exactly what the form needs to collect, so this is the fastest path to
   shipping something and can be upgraded later.

This needs a decision before implementation starts (see open questions).

## 5. Data model

Move from "one local SQLite file per machine" to a small multi-tenant schema:

- `users` — account/auth
- `strava_tokens` / `coros_tokens` — per-user credentials (encrypted at rest)
- `activities` — same shape as today's `activities` table, keyed by `user_id`
- `plans` — the generated `TrainingPlan` JSON blob + metadata (id, user_id, created/updated),
  replacing the flat `{event}-{date}.json` file convention
- `plan_edits` — the completion/move/edit history currently kept in `localStorage`'s `changes`
  store, so edits sync across devices

`src/db/schema.sql`'s activity/athlete tables translate almost directly — just add `user_id` and
move off single-file SQLite to whatever the app's chosen backend is (Postgres is the safe default
for a multi-tenant hosted app; SQLite is fine if this stays self-hosted/single-tenant).

## 6. Phased delivery

Each phase produces something runnable, so the migration can be checkpointed rather than done as
one big-bang rewrite.

1. **Headless engine, still CLI-driven.** Build `coach-engine` as a library + a new
   `claude-coach generate` CLI command that calls the Claude API directly (using an API key from
   the environment) against already-synced Strava/manual data, producing a validated plan JSON —
   no human running the skill by hand. This de-risks the prompt/tool/validation work in isolation,
   reusing today's local-file storage so there's no infra to stand up yet.
2. **Backend + auth.** Stand up the multi-tenant DB and API routes; move Strava OAuth
   server-side; wrap the Phase 1 engine behind `POST /api/generate-plan`.
3. **Onboarding UI.** Build the wizard that replaces the conversational data-gathering — event
   details, constraints, data-source choice, manual-entry form matching `SKILL.md` §"Option B".
4. **Live viewer.** Point `App.svelte` at `/api/plans/[id]` instead of embedded JSON; wire edits
   back to the backend; keep the static `render` export as a secondary output.
5. **Assessment review + regeneration loop.** The "present assessment, validate, adjust" step as
   an editable screen that triggers a second, corrected generation call.
6. **COROS integration**, per whichever option is chosen in §4.2.
7. **Decide the skill's fate.** Ship the app and the skill side by side for existing Skill users
   (`coach-skill.zip` costs little to keep publishing), or fold the skill into a thin wrapper
   that just links to the app, once the app covers the same ground.

## 7. Open questions (need a decision before implementation)

- **COROS integration path** (§4.2): direct API, direct MCP client, or manual-only for v1?
- **Hosting model**: single hosted multi-tenant service (you run it, users sign up), or a
  self-hostable app users run themselves (closer to today's local-CLI model, simpler auth, no
  "who pays for Anthropic API usage" question)?
- **Who pays for Claude API usage**: app operator's API key (usage costs scale with users), or
  let each user supply their own key (keeps the app's marginal cost at zero, adds setup friction)?
- **Keep the npm CLI package** (`claude-coach`) alongside the web app, or fold `sync`/`render`
  into the app and retire the standalone CLI?
- **Strava vs. COROS as the primary/only integration** — the README still centers Strava/
  triathlon; confirm the running+strength/COROS direction from the latest `SKILL.md` commits is
  the one to build the app around, and update or retire the README accordingly.
